# データ設計の見直し（出社イベントの永続化と高速起動）

- 作成日: 2026-11-02
- 状態: 承認済み（2026-11-02、§10 の決定事項を反映）
- 対象: hikarie-bot のデータ取得・保存・集計・配布の全体

## 1. 背景と目的

起動のたびに Slack のチャンネル履歴を全件取り直して DB を作り直しており、再起動・デプロイのたびに長時間止まる。
これを解消し、コードの改善をすぐ本番に届けられる構成にする。

制約:

- 本番で使えるのは「ghcr.io からイメージを pull して Rancher 2.9.3 で動かす」範囲のみ。
- 出社データ（Slack ユーザーID と出社時刻）は機微情報として扱い、**ネット上（イメージ・CI・リポジトリ）には一切置かない**。
- Rancher では PVC が使える（StorageClass: `ebs-sc` / `gp2`、`kubectl auth can-i create persistentvolumeclaims` = yes）。

## 2. 調査結果

### 2.1 本番環境の設定

| 項目 | 結果 | 影響 |
|---|---|---|
| DB | `.env` は `DATABASE_URL=...` だが、コードは `URL` を読む（`settings.py`）。結果として **`sqlite:///:memory:`** で動いている | 再起動のたびにデータが消え、全件の取り直しが必須になっている |
| Bot トークンのスコープ | `chat:write, channels:history, reactions:read, reactions:write, users.profile:read, commands` | `channels:read` / `users:read` は無い。チャンネルメンバー一覧などは取れないが、本設計では不要 |
| イメージ | `hikarie-bot` は匿名 pull 不可（private と思われる）。`hikarie-bot-initial-data` は **public**（中身は空の manifest のみ。public→private には戻せない） | データイメージ方式は採らない（§8） |

### 2.3 起動時のコスト（現行）

| 処理 | 呼び出し回数 | 時間 |
|---|---|---|
| `conversations.history`（既定 limit で全件） | 約 60 回 + 各 `sleep(1)` | 約 1.5 分 |
| `conversations.replies`（v3 の親ごと） | 502 回 + 各 `sleep(1)` | **約 12〜13 分**（実測 1.58 秒/回） |
| 取り込み＋バッジ計算（`insert_arrival_action` を 3,428 回） | — | 102 秒（実測） |
| 合計 | | **約 15 分**。しかも回数はスレッド数に比例して増え続ける |

計算部分は 1 件あたり約 30ms（1,000 件ごとに 26s → 30s → 32s と増加）。1 件ごとに 20 前後の SQL を発行し、
多くが「その人の全履歴の件数」を数えるため、履歴が伸びるほど遅くなる。

### 2.4 現行コードの設計上の問題

データモデル:

1. **派生データを逐次更新で保存している。** `GuestArrivalInfo.arrival_rank` / `acquired_score_sum`、`User`、`UserInfoRaw`、`Achievement`、`UserBadge` を 1 件ずつ到着順に書き足す。
   順序に依存するため、遅れて届いたイベント（過去日付）を正しく反映できず、バッジ規則を変えても再計算する手段が「全件取り直し」しかない。
2. **生データに一意キーが無い。** `GuestArrivalRaw` は取り込むたびに重複する。どの Slack メッセージ由来かも記録していない。
3. **マスタ（`Badge` / `BadgeType`）を DB に複製している。** `initially_insert_badge_data` はテーブルが空のときしか入れないため、DB を永続化すると新しいバッジが入らず、`.one()` が例外になる。
   今まで問題にならなかったのは、メモリ DB で毎回作り直していたから。
4. スキーマの不整合: `user_info_raw_id` が一意でない `user_raw.user_id` を外部キー参照、`UserBadge.user_id` が Integer（`User.id` は String）、`(user_id, 日付)` の一意制約が無い。
5. 日時のタイムゾーンが混在（aware で計算し、SQLite で naive として保存・比較）。commit 後の再読み込みで偶然揃っているだけ。

処理:

6. `check_straight_flash` に `@lru_cache` がかかっており、`Session` を含む引数でキャッシュされる（セッションをまたいで ORM オブジェクトが残る）。
7. 週次メッセージのタスクは、`with get_db()` を抜けて close されたセッションを使い続けている（週次レポートは廃止したため解消）。
8. `get_db()` が呼ばれるたびに `create_all` を実行している。
9. 判定の一部が「挿入順（`id`）」や「判定時点の現在時刻」に依存しており、再計算すると結果が変わり得る（`check_lucky_you_guys`、`check_yearly_specific_day` の年度末/年度初め）。
10. 出社時刻の基準が経路で異なる。ボタン押下時はクリック時刻、履歴からの再構築時はスレッド投稿の ts（数秒後）。分単位のバッジ（11:11 など）が境界で変わり得る。
11. `filter_v2` が v2 用の正規表現ではなく v1 用を使っている（結果的に動いているが意図と異なる）。

運用:

12. ローカルで本番の App トークンを使って Socket Mode で起動すると、本番と同じアプリに接続し、**ボタン押下イベントがローカルに奪われる**。手元での確認には別アプリか、オフライン実行が必要。

### 2.5 対応状況（`rebuild`）

| # | 問題 | 対応 |
|---|---|---|
| 1 | 派生データの逐次保存 | 出社イベントだけを保存し、エンジンで毎回一括計算（#124, #125） |
| 2 | 生データに一意キーが無い | `arrival_event`（Slack ts で一意）に置き換え、`GuestArrivalRaw` を削除（#121, #125） |
| 3 | マスタを空のときだけ投入 | 起動のたびにコードと同期（#121）。その後、派生テーブルとともに DB から削除し、コードだけを正とした（リビジョン 0001） |
| 4 | スキーマの不整合 | 新テーブルは正しい型と制約で作成。旧テーブルの不整合は派生テーブルごと削除して解消（リビジョン 0001） |
| 5 | タイムゾーンの混在 | イベントはタイムゾーン付き UTC で保存し、naive な日時は拒否（#121） |
| 6 | `lru_cache` の誤用 | `BadgeChecker` ごと削除（#133） |
| 7 | 閉じたセッションの使い回し | 週次レポートごと削除（#131） |
| 8 | セッションごとの `create_all` | プロセスごとに 1 回のマイグレーションに変更（#121） |
| 9 | 挿入順・現在時刻への依存 | エンジンは常に時刻順に計算するため結果は一意。実データでは差分なし |
| 10 | 経路による時刻のずれ | 新しい出社は押下時刻をメッセージ metadata に残す（#127, #128）。過去分は投稿時刻のまま |
| 11 | `filter_v2` の正規表現 | v1/v2 の投稿を書式（`最速出社申告ユーザ：<@…>`）と期間で判定し、`V1_BOT_ID` / `V2_BOT_ID` の設定ごと廃止。実データの結果は同一 |

このほか、営業日が 2 週間で 5 日未満だとストレートフラッシュ判定が例外で止まる潜在的な不具合を修正した（実データの結果は変わらない）。

## 3. 方針

1. **出社イベント（生データ）とアイテムの選択だけを正として永続化する。** バッジ・スコア・ランク・レベルはすべて「イベント列＋コード上の規則」から計算する派生物とし、保存されたものを正としない。アイテムの選択は本人の操作で、出社イベントから導けないため、これだけは別に記録する（§4.3）。
2. **派生物は起動時にメモリ上で一括計算する。** 1 パス O(N) の純粋な計算に置き換え、数千件なら 1 秒未満を目標にする。規則を変えたらデプロイするだけで全履歴に反映される。
3. **永続化は Rancher の PVC 上の SQLite。** Slack からの全件取り込みは初回（と PVC 喪失時）だけ。以降の起動は Slack を読まない。
4. **データはネットに置かない。** データイメージ・暗号化スナップショットは作らない。手元では named volume と、Slack 応答の生キャッシュを使う。
5. **マスタはコードを正とする。** DB に置く場合も起動時に毎回同期する。

## 4. データモデル

### 4.1 永続化するテーブル

```text
arrival_event                       -- 出社の事実（追記のみ）
  id            INTEGER PK
  user_id       TEXT    NOT NULL    -- Slack ユーザーID
  occurred_at   TEXT    NOT NULL    -- UTC の ISO8601（タイムゾーン付き）
  source        TEXT    NOT NULL    -- 'slack_v1' | 'slack_v2' | 'slack_v3' | 'button'
  slack_ts      TEXT    UNIQUE      -- 根拠となる Slack メッセージの ts（ボタン経由で投稿前なら NULL）
  recorded_at   TEXT    NOT NULL

item_pick_event                     -- アイテムの選択（追記のみ、リビジョン 0003）
  id            INTEGER PK
  user_id       TEXT    NOT NULL
  day           DATE    NOT NULL    -- 選んだ JST の日。(user_id, day) で一意＝1 日 1 回
  item_id       TEXT    NOT NULL    -- db_data/items.py の ID
  occurred_at   TEXT    NOT NULL    -- UTC の ISO8601
  slack_ts      TEXT    UNIQUE      -- スレッドの告知投稿の ts（投稿前なら NULL）
  recorded_at   TEXT    NOT NULL

alembic_version                     -- Alembic のリビジョン（0000 が基準）
```

- 同じ人の同じ日（JST）に複数のイベントがあっても許容し、**計算時に最初の 1 件を採用**する。これで「ボタンで記録 → その後の同期で同じ投稿を再取得」も、`slack_ts` の一意制約と合わせて冪等になる。
- ボタン経由: 押下時にイベントを記録（`occurred_at` = 押下時刻）→ スレッドに投稿 → 投稿の ts を `slack_ts` に書き戻す。

### 4.2 派生データ

計算結果（日ごとの到着・順位・獲得バッジ・スコア推移・レベル）は、計算エンジンの出力として保持する。

- 第 1 段階: 既存のテーブル（`GuestArrivalInfo` / `Achievement` / `UserBadge` / `User` / `UserInfoRaw`）に**毎回作り直す形で書き出す**。既存のメッセージ組み立て処理（`modals.py`）を変えずに済む。
- 第 2 段階（実施済み）: メッセージ組み立てを計算結果（`BadgeEngine`）から直接読むように移し、これらのテーブルと `Badge` / `BadgeType` をリビジョン 0001 で削除した。
  ボタン押下と実績表示のたびに全イベントから計算し直す（合成データ 3,400 件で約 50ms）。エンジン内の時刻は JST の aware datetime で、naive な JST を保存・比較する箇所は無くなった。

### 4.3 アイテム

- 「出社した」「実績を確認」の横の「今日のアイテム」から、3 つの候補のうち 1 つを選ぶ。候補は `(user_id, 日付)` のハッシュで決まるので保存せず、選んだものだけを保存する。サイコロの出目も同じく `(user_id, 出社日)` から決まる。
- 選べる条件: その日の出社が告知済み（`slack_ts` あり）、その日まだ選んでいない、アイテムを持っていない（1 人 1 個まで）。ボタンを押したときとモーダルの送信時の両方で確かめる。
- 効果は選んだ日より後の出社にだけ及ぶ。選択は必ずその日の出社の後なので、選択がその日の結果を変えることはない。
  - 1 回きり（`duration_bizdays` なし）: 次の出社 1 回。何日空いても持ち越す。使うまで「持っている」。
  - 期限付き（`duration_bizdays` あり）: 選んだ翌営業日から N 営業日の出社すべて。最終日まで「持っている」。
- アイテムによる加点は 1 回の出社につき 3pt まで（`ITEM_POINT_CAP`）。起動時のレポートに、全体の点のうちアイテム由来の割合を出してインフレを監視する。
- 告知はスレッドへの控えめな 1 行（context ブロック、`reply_broadcast` なし）で、metadata `event_type: hikarie_item_pick` を付ける。同期はこれを読んで `item_pick_event` を復元する。出社と同じく「記録 → 投稿 → ts の書き戻し」で、投稿に失敗した選択は次にボタンを押したときに告知し直す。

## 5. 計算エンジン

- 入力: `arrival_event` を時刻順に並べ、人×日で先頭 1 件に絞った列。
- 状態: 人ごとの到着日時の列・累計回数・初回日、全体の累計回数（キリ番）、日ごとの到着順、分ごとの到着数など。
- 各バッジ判定は「その時点までの状態」を受け取りバッジ ID を返す純粋関数にする（SQL を発行しない）。
- 出力: 到着ごとの順位・獲得バッジ・獲得点、人ごとのスコア推移とレベル。
- ライブのボタン押下時も同じエンジンに 1 件追加して差分計算する。過去日付のイベントが入った場合は全体を再計算する（それでも 1 秒未満）。

### 5.1 正しさの担保

- 手元の生キャッシュ（§7）から作ったイベント列を、**現行コードと新エンジンの両方**で計算し、到着ごとのバッジ・点数・順位を比較するゴールデンテストを用意する。
  実データはリポジトリに入れないため、このテストはキャッシュがある環境でだけ動かし、CI では合成データ版を動かす。
- 1,400pt を超えたときの扱い（#107: レベル 12 で止まり、上限到達はレベルアップに数えない）も新エンジンに引き継ぐ。
- §2.4 の 6・9・10 は直す（過去のポイント・バッジが変わることは許容済み、§10-1）。ただし、まず現行と同じ結果になることをゴールデンテストで確認してから直し、直した結果どの到着のバッジ・点数が変わったかを差分として出して確認する。

## 6. Slack との同期

| 場面 | 処理 | 呼び出し回数の目安 |
|---|---|---|
| 初回（PVC が空） | 全件取り込み。`conversations.history`（limit 200）全ページ ＋ v3 の親ごとに `conversations.replies` | 約 540 回・約 13 分（初回のみ） |
| 通常の起動（`arrival_event` が空でない） | 読まない（ログチャンネルには件数だけ報告） | 0 |
| 稼働中 | ボタン押下でイベントを記録（Slack への再問い合わせなし） | 0 |
| 古いバックアップの復元後 | 手動で `python -m hikarie_bot sync`（全件取り込み。冪等） | 約 540 回・約 13 分 |

- ボタン押下は「記録 → 投稿 → ts の書き戻し」の順で、本番は 1 レプリカ（`Recreate`）・1 PVC なので、Slack にあって DB に無い出社は生じない。そのため差分同期（位置の `sync_state`、1 日の重なり読み）は持たず、リビジョン 0002 で `sync_state` を削除した。
- 同期は常にチャンネル全体を読む。返信が `reply_count` に満たないスレッドは警告を出す（再実行で補える）。
- 取り込みは `slack_ts` で重複排除するので、何度実行しても同じ結果になる。
- レート制限は `slack_sdk` の `RateLimitErrorRetryHandler` に任せ、固定の `sleep(1)` は外す。
- スレッド投稿に Slack のメッセージ metadata（`event_type: hikarie_arrival`、押下時刻と user_id）を付ける（§10-2）。追加のスコープ不要で、履歴からの再構築でも押下時刻を正確に復元できる（§2.4-10 の解消）。metadata の無い過去の投稿は、従来どおり投稿の ts を出社時刻とする。

## 7. 起動シーケンスと実行環境

### 7.1 起動シーケンス

1. DB を開き、Alembic でスキーマを最新リビジョンに上げる（SQLite は WAL モード）。リビジョン 0000 より前の形式の DB は引き継がず、起動を止める（データは Slack から作り直す）。
2. `arrival_event` が空のときだけ Slack から全件取り込み（初回と PVC 喪失時）。空でなければ読まず、`slack sync: skipped (N events stored)` と件数だけ報告する。
3. 計算エンジンで一括計算し、結果を報告する（保存はしない）。
4. Socket Mode 接続、日次タスク開始。

通常の再起動は 10 秒未満を目標にする。

### 7.2 本番（Rancher 2.9.3）

手順とマニフェストは [docs/deploy/rancher.md](../deploy/rancher.md) と `deploy/rancher/` にある。

- PVC: StorageClass `ebs-sc`、1Gi、ReadWriteOnce。
- Deployment: `replicas: 1`、**`strategy: Recreate`**（EBS は 1 ノードにしかマウントできず、ローリング更新だと新 Pod が起動できない）。
- `securityContext.fsGroup: 10001`（コンテナは UID 10001 で動くため、ボリュームを書き込み可能にする）。
- 環境変数: `DATABASE_URL=sqlite:////data/hikarie.db`（`URL` は読まない。dev/test 以外では必須で、未設定ならメモリ DB に落ちず起動エラー）。
- イメージは `ghcr.io/xilorole/hikarie-bot:sha-xxxx` のようにタグを固定し、既存の imagePullSecret を使う。
- EBS はアベイラビリティゾーンに紐づくため、Pod はそのゾーンのノードにしか配置されない。

### 7.3 手元（ローカル開発）

- `docker compose` の bot サービスに named volume を付けて DB を永続化する（PVC 相当）。
- **Slack 応答の生キャッシュ**: `/Users/<you>/hikarie-bot/.cache/slack/<channel>/` に、API の応答本体をそのまま保存（gitignore・dockerignore 済み）。
  `python -m hikarie_bot sync --record <dir>` で記録し、`python -m hikarie_bot sync --from-cache <dir>` で Slack にアクセスせず DB を作り直す。
- **書き込み防止**: 書き込み API を止める dry-run モードは作らない。開発用アプリを `slack run` で開発用ワークスペースに立てれば本番のチャンネルには書き込まないため、それで足りる（次の項目）。
- §2.4-12 のため、手元で Socket Mode を動かす場合は**開発用の Slack アプリ**を使う（§10-3）。main に入った `slack run`（#109、開発用ワークスペースに開発用アプリを立てる）をそのまま使う。本番アプリのトークンでは接続しない。
- メッセージの見た目は `python -m hikarie_bot preview` で Block Kit Builder の URL を発行して確認する。

## 8. 廃止するもの

| 対象 | 理由 |
|---|---|
| `hikarie-bot-initial-data` イメージ、`initial_data.py`、Fernet 暗号化、`cryptography` 依存、関連する CI ジョブと compose サービス | データをネットに置かない方針のため不要。public の空パッケージは削除する（§10-5）。release workflow が push するたびに作り直されるため、**CI ジョブを撤去してから**削除する |
| 起動時の全件取り込み（`initially_create_db`）と `--skip-db-create` | DB が空のときだけの全件取り込みに置き換え |
| `GuestArrivalRaw` | `arrival_event` に置き換え |
| 派生テーブル群と `Badge` / `BadgeType`（実施済み、0001） | 計算結果を直接使う形に移行 |

## 9. 実装フェーズ

各フェーズは小さな PR に分けて統合用の `rebuild` ブランチへ入れ、すべて置き換わってから `rebuild` を main にマージする。

1. **設定とスキーマ**: pydantic-settings による設定（`DATABASE_URL` のみ）、`arrival_event`・`sync_state`、Alembic によるマイグレーション（旧形式との互換なし）、マスタの毎回同期、initial-data 関連の撤去。
2. **同期**: 全件取り込み・差分同期・`slack_ts` による重複排除、生キャッシュへの記録とキャッシュからの再構築。
3. **計算エンジン**: 純粋関数のバッジ判定と一括計算、既存テーブルへの書き出し、ゴールデンテスト（実データはローカルのみ）。
4. **ライブ経路の切り替え**: ボタン押下 → イベント記録 → エンジンで差分計算 → 投稿。
5. **デプロイ**: Rancher の PVC・Deployment 設定例と手順書、public の initial-data パッケージの削除。
6. **後続**: 派生テーブルの廃止（メッセージ組み立てを計算結果から直接読む形へ）。実施済み。

§2.4-6・9・10 の修正は 3 で、メッセージ metadata は 4 で行う。
